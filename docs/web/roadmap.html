Processus de travail

Le cycle appliqué à chaque fonctionnalité, du début à la fin.

  1. Lire context.md et les documents concernés.
  2. Créer une branche dédiée : feat/…, fix/…, docs/….
  3. Développer par petites étapes, en commits atomiques au format Conventional Commits.
  4. Tester : php tests/run.php, puis vérifier l'interface dans le navigateur.
  5. Mettre à jour la documentation, context.md, projet.json (puis php docs/tools/sync.php) et le registre des anomalies.
  6. Commit et push, sans aucune mention de co-auteur.
  7. Ouvrir une pull request avec gh pr create.
  8. Fusionner après validation (automatique pour la documentation et les corrections mineures).
  9. Supprimer la branche fusionnée et confirmer la mise à jour de context.md.

Mettre à jour

Une seule source, trois vues synchronisées.

Toutes les données de suivi (exigences, statuts, phases, propositions) vivent dans docs/web/data/projet.json. Après modification, lancer php docs/tools/sync.php : la commande régénère projet.js, lu par cette page et par le cahier des charges, ainsi que docs/03-suivi/suivi-cahier-des-charges.md. Les trois vues restent donc toujours d'accord.

Ces pages s'ouvrent directement depuis le disque (double-clic) ou via l'application, à l'adresse /projet/.
